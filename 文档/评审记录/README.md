# 评审记录

每次评审留一份报告，随 PR 进仓库 —— 谁评审的、看了什么、发现了什么、怎么处理的、
结论是什么，全程可追溯，不依赖聊天记录。

命名：`R<PR号>-<YYYYMMDD>-<主题简述>.md`

## 角色约定

本项目的规则**只按角色立规，不绑定具体工具**。三个角色：

| 角色 | 职责 | 产出 |
|---|---|---|
| **执行者** | 读谱、标注、改 spec、改 PR 正文、提交推送 | 分支 + PR + 与代码同步的 PR 正文 |
| **评审者** | 独立复核、验证、提修正意见、出评审报告 | 评审报告 + PR 评论 + 「可合并 / 有条件通过 / 打回」结论 |
| **观察者** | 决定合并与否、控制节奏、跟踪进展 | 合并动作 |

同一角色可以由不同的人或 agent 承担，规则不变。
涉及具体工具名时一律写成「**以 X 为例**」，那是举例，不是规则的一部分。

## 报告要写清

- **审查范围** —— 改了哪些文件、多少规模、涉及哪些排
- **客观验证数据** —— 直接贴脚本输出
- **人工复核抽样** —— 挑几个音对着谱面核，说明依据
- **发现的问题** —— 分高/中/低三级，写明处理方式
- **结论与遗留** —— 三选一：通过 / 有条件通过 / 打回
- **合并前必做清单** —— 见下方第 4 条

## 四条原则

1. **结论必须挂数字** ——「看着对」不算，要有脚本输出或人工复核记录
2. **问题分级** —— 只有高等级（影响正确性）必须本次修
3. **不推翻已验证的规则** —— 推翻必须给出新的独立证据，不能只靠推理
4. **「可合并」= 正文已同步** —— 见下

## 第 4 条展开：正文同步必须先于合并

PR 正文（description）里的读数表是**代码的对外说明**。若正文停留在修正前的旧值，
后来人读到的就是错数据 —— 哪怕代码完全正确。

**硬性顺序**（R23/PR #24 教训：正文未同步就合并，只能靠事后补改）：

```
执行者初版  →  评审者提修正  →  执行者改代码  →  执行者同步正文
           →  评审者复核通过  →  观察者合并
```

**合并前必做清单**（评审者复核通过时必须逐条确认，缺一条就不给「可合并」结论）：

- [ ] PR 正文读数表与 spec 逐音一致（修正过的音，正文也必须跟着改）
- [ ] 正文的「修正说明」段落写清了本轮改了什么、依据是什么
- [ ] 正文贴的校验数字与当前代码重跑结果一致
- [ ] 分支已推最新，PR 与 main 无冲突
- [ ] 远端已合并分支已清理

**给观察者的行动清单也要按这个顺序排**：先「同步正文」，再「合并」。
把合并排在前面、正文排在后面，等于把「可合并」的结论建立在未完成的动作上。

若已合并才发现正文过时：正文仍可编辑（`gh pr edit <n> --body-file`），补改并留注释说明，
同时在 issue 里写明**以代码为准**。
